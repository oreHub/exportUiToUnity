# 提案資料のための情報まとめ — PSD から Unity UI を作る仕組み（exportUiToUnity）

作成: 2026-10-18 ／ 対象: claude.ai で社内向けの提案資料（スライド）を作るための元資料

## この文書の使い方（claude.ai へ）

- この文書だけで提案資料が作れるように、背景・仕組み・実機で確かめた結果・今後をまとめている
- 聞き手は、ゲーム開発の社内（UI デザイナー、エンジニア、ディレクター・リード）を想定する
- 伝えたいことの柱は 3 つ:
  1. **デザインの PSD から、Unity の UI を機械的に組み立てられる**（手で並べる作業と、指示書の往復を減らす）
  2. **デザインを直しても、エンジニアの作業を壊さずに反映できる**（協業できる）
  3. **間違いを早く見つけ、勝手に決めずに人に確かめる**（確実さ）
- 「できていること」と「これから」を分けて書くこと。実機で確かめた範囲を誇張しない
- 社内資料なので、ほかのプロジェクトの固有名は入れない

## 1. 背景と課題

ゲームの UI 制作では、次の往復が毎回発生している。

1. デザイナーが Photoshop で画面をデザインする
2. Unity での組み方（階層・位置・並び・画像の切り出し）を指示書に書く
3. エンジニアが指示書を読みながら、Unity で手で並べる
4. デザイナーが確認し、ずれや抜けを伝え、直してもらう
5. デザインが変わるたびに 2〜4 を繰り返す

課題:

- 指示書を書く・読む・手で並べる作業に時間がかかる
- 人の手を通すので、位置や間隔のずれ、画像の切り出し漏れが起きる
- デザインを直すと、エンジニアが付けた処理（ボタンの動作など）とぶつかり、反映が怖くなる

## 2. 解決の考え方

- **PSD に構造の情報を持たせる**: デザイナーがレイヤー名に「印」（`_Grp`・`_List`・`_Prefab` など）を付ける。
  全部を自動判定するのではなく、印で明示する（複雑な PSD では自動判定が外れるため）。ツールは印の抜けを「提案」として出す
- **Unity の UI 構造と画像は、機械的に作る**: PSD から書き出したデータ（layout.json と画像）を、Unity の取り込みツールが組み立てる
- **直すのは PSD だけ**: 構造を直す場所を 1 か所にする（レポートや Unity で直すと、どちらが正しいか分からなくなる）
- **最終決定は Unity の取り込み**: 書き出しはエラーがあっても止めない（ダブルチェックと相談に使う）。取り込みで確認を求める

## 3. 仕組みの全体像

```
PSD（レイヤー名に印）
  │  [Photoshop プラグイン] 解析 → 問題の一覧 → 名前で直せるものはボタンで直す → 書き出し
  ▼
<Unity プロジェクト>/UIExport/<画面ID>/   ※Assets の外。git で共有
  layout.json（構造データ）・images/（部品ごとの画像）・report.html（人が見るレポート）・history.json（版の記録）・preview.png
  │  [Unity 取り込みツール] 取り込み（新規）／反映（更新）
  ▼
Unity のシーン: Canvas の下に画面の GameObject・Prefab
  （後の段階）[After Effects パネル] layout.json から AE ファイルを作り、付けた動きを Unity に当てる
```

### ツール（1 つのリポジトリ `exportUiToUnity` にまとめている）

| ツール | 動く場所 | 役割 | 状態 |
| --- | --- | --- | --- |
| Photoshop プラグイン（`exportPsdToUnity_plugin`） | Photoshop（UXP パネル） | PSD を解析・検査・修正し、UI の構造と画像を書き出す | 解析・修正・書き出し まで実機で確認（0.3.0） |
| Unity 取り込みツール（`buildUiToUnityPackage`） | Unity エディタ（UPM パッケージ） | layout.json と画像から uGUI の画面を組み立てる。更新を反映する | 新規の取り込み と 反映 まで実機で確認（0.3.0） |
| After Effects パネル（`exportAeToUnity_plugin`） | After Effects | AE ファイルの構築、動きの検査と書き出し | 計画のみ（未着手） |

名前の決まり: Adobe 側で書き出すものは `export〜`、Unity 側で組み立てるものは `build〜`。末尾は最終の形（`_plugin` = パネル、`Package` = Unity パッケージ）。

## 4. 各ツールでできること（今の状態）

### Photoshop プラグイン

- **解析**: レイヤー名の印を読み、Unity での構造（階層・並び・Prefab・画面端への固定など）を組み立てる。約 100 レイヤーで 0.1 秒未満
- **問題の一覧**: エラー・注意・提案・情報の 4 段階。項目やレイヤー名を押すと、そのレイヤーが選ばれる
  - 例: 名前の重複、ID に使えない文字、並びの間隔の不揃い、文字の枠からのはみ出し、Prefab の構成の違い、綴りの揺れ、印の付け忘れ
- **名前で直せる提案はボタンで直す**: `_Prefab` / `_Grp` / `_List` / `_Base` を付ける、綴りを直す、重複に連番を付けるなど。取り消し 1 回で戻せる。
  位置や構造の変更は人が判断する（ボタンにしない）
- **書き出し**: 部品ごとの画像（同じ絵は 1 枚を共有）、layout.json、report.html、history.json、preview.png
  - 画像は Photoshop 自身で書き出す（レイヤースタイル・不透明度は焼き込み）
  - **版の管理**: 書き出すたびに `YYMMDD-n` の版が付き、PSD の中（XMP）に「元にした版」を記録して保存する。
    古いバックアップの PSD から書き出そうとすると止めて知らせる。何も変わっていなければ版を増やさない
  - 前の版との差分をレポートに出す

### Unity 取り込みツール

- **取り込み（新規）**: 今のシーンに追加する／保存先を選んで新しいシーンを作る
  - Canvas（画面の大きさに合わせて拡大縮小）、Image、TextMeshPro の文字、Horizontal / VerticalLayoutGroup（並び）
  - `_Prefab` の型ごとに **Prefab を 1 つ** 作り、ほかは同じ Prefab のインスタンスにして画像・文字だけ差し替える
    （例: フッターの 6 個のボタンは 1 つの Prefab と 6 個のインスタンス）
  - エラーのある版は、取り込む前に確認を求める
- **反映（更新）**: デザインを直して書き出し直したとき、Unity の画面を作り直さずに更新する（次の章）

## 6. エンジニアとの協業: デザインの更新を、エンジニアの作業を壊さずに反映する

### 想定する流れ

1. デザイナーが書き出し、エンジニアが Unity に取り込む
2. エンジニアが、ボタンに処理（スクリプト・押したときの動作）を付けたり、位置を調整したりする
3. デザイナーが PSD を直して書き出し直す
4. エンジニアが「反映」を押す → **これから行う変更の一覧** を確かめて「確定」

### 反映の決まり

- **部品の照合**: PSD の部品と Unity の GameObject を結び付ける。① 名前が同じ → ② PSD のレイヤー番号が同じ（名前の変更・移動にも付いていく）
  → ③ それでも見つからず、エンジニアの作業がある部品は、人に「どれと同じか」を聞く
- **値の比べ方（3 方向）**: 部品の値ごとに「前に取り込んだ値」「今の Unity の値」「新しい PSD の値」を比べる

  | 場合 | 扱い |
  | --- | --- |
  | Unity で誰も触っていない | デザインの変更として更新する |
  | エンジニアが変えていて、PSD とも違う | **自動で決めない。** 必ず人が「PSD の値にする」「Unity の値を残す」を選ぶ（エンジニアの変更が操作ミスのこともあるため） |
  | エンジニアが足したスクリプト・部品 | 触らない |

- **PSD から消えた部品**: エンジニアの作業が無ければ削除。あれば消さずに非表示で残して知らせる
- **元に戻せる**: 反映は Unity の取り消し 1 回で戻せる
- **逆方向への準備**: 「Unity の値を残す」を選んだものは「PSD に戻す候補」として記録する（後で、Unity での調整を PSD に戻す機能に使う）

### 実機でのテスト結果（2026-10-18）

1. 版 261017-3 を取り込み、エンジニアの作業のつもりで、フッターにボタンのリストと遷移先を持つスクリプト、各ボタンにスクリプトと押したときの動作を付けた。
   さらに Battle ボタンを Unity で 100px 動かした
2. PSD でフッターを左に寄せて書き出した（版 261018-1）
3. 反映すると、一覧は次のとおり
   - デザインの変更として更新: フッターの位置（1 件）
   - 選んでください: Battle ボタンの位置（前に取り込んだ値 808.5 / 今の Unity 708.5 / 新しい PSD 808.5）
4. 確定後、フッターは左に移り、**付けたスクリプト・リスト・押したときの動作はすべて残った**。Battle ボタンは選んだとおりになり、その値は「PSD に戻す候補」に記録された

## 7. 決めたことと理由（抜粋）

| 決めたこと | 理由 |
| --- | --- |
| 全部を自動判定せず、印で明示する。抜けは「提案」として出す | 複雑な PSD では自動判定が外れる。間違いは必ず出るので、一覧にして直せるようにする |
| 直すのは PSD だけ | 直す場所が 2 つあると、どちらが正しいか分からなくなる |
| エラーがあっても書き出せる。止めるのは Unity の取り込み | 書き出しはダブルチェックと相談に使う。取り込みが最終決定 |
| 版は書き出し時に付け、PSD に「元にした版」を記録する | 保存のたびに付けると無意味な版が増える。複製しても続きと分かる |
| 反映で差がある所は、必ず人が選ぶ | エンジニアの変更もデザインの変更も、どちらが正しいかは場合による |
| 追いかける必要があるのは、エンジニアの手が入った部品だけ | 飾りの部品は作り直しても失うものが無い。細かいデザイン検討を妨げない |
| 3 つのツールを 1 つのリポジトリに置く。データの形（layout.json）の正は共通の資料 | 書く側と読む側を同時に直せる |
| Unity ツールは UPM パッケージで配る | 配るのはパッケージだけ。開発用の資料やテスト用プロジェクトは配らない |

## 8. これから

### 予定している機能（着手の順番が後というだけで、入れる）

- **Unity での調整を PSD に戻す**: エンジニアが Unity で位置を調整し、それが正となったとき、手作業なしで PSD に反映する。
  Unity 側で変更を書き出し、Photoshop プラグインで一覧から選んでレイヤーを動かす（「直すのは PSD だけ」を保ったまま、手作業を減らす）
- **PSD 側での早期警告と付け直し**: 書き出しのとき、前の版にあった部品が見つからなければ警告する。新しく作り直したレイヤーを選んで「付け直す」と、
  Unity では同じ部品として更新される（作り直しによる取り違えを、PSD の段階で防ぐ）
- **アニメーション**: layout.json から After Effects のファイルを作り（Unity と同じ親子関係・ピボット）、AE で付けた動きを検査して書き出し、Unity に当てる
- **効果の分割（`_Fx`）**: 光彩・影・境界線を別画像に分け、Unity で色を変えたり動かしたりできるようにする
- **データの形の版（format_version）**: ツール同士の食い違いを検出する

### ブラッシュアップ項目（実機の確認で出た課題）

- Prefab の中の非表示レイヤー（バッジなど）を「初期状態では非表示の部品」として扱う
- Prefab のまとめ方を分かりやすくする（親が違う場所の同じ型をまとめる、Prefab の名前を決められるようにする）
- 部品の基準の範囲（例: アイコンが基準で、バッジは付属物）などのデザインの指針を、規則として取り入れる
- パネルの「間隔」の数字を、デザインと同じ「外形同士のすき間」で出す
- 文字と文字の枠のずれを直接指摘する
- フォントの対応（今は Unity の既定のフォント）

### 運用で決めていくこと

- 「〇〇ボタン」のような大きな単位のフォルダは入れ替えず、その中で追加・削除する（作り直しによる取り違えを防ぐ）
- 修正と更新の流れ、エンジニアが先に作る場合・同時に進める場合の進め方

## 9. 今の制約・注意

- 文字は Unity の既定のフォント（PSD のフォントとの対応は未実装）。配置は合うが見た目の文字は違う
- 反映では Prefab の元のファイルは更新せず、インスタンスごとの差し替えとして反映する
- After Effects パネル、効果の分割、Unity → PSD は未着手
- 確認はサンプル画面 1 つ（Home）。ほかの画面での確認はこれから

## 10. 用語

| 用語 | 意味 |
| --- | --- |
| 印 | レイヤー名の末尾に付ける目印。`_Grp`（GameObject として残す）、`_List`（並び = LayoutGroup）、`_Prefab`（Prefab にする）、`_Img`（中身ごと 1 枚の画像）、`_Base`（親自身の画像） |
| area_ / space_ | 名前の先頭に付ける領域・間隔の指定。画像にはならず、構造の情報としてだけ使う（枠、文字の枠、間隔、画面端からの距離） |
| layout.json | PSD から書き出す構造データ。ツール同士の受け渡しに使う（人が読むものではない） |
| 版 | 書き出しごとに付く番号（例 261018-1）。PSD に「元にした版」を記録する |
| 取り込み / 反映 | Unity で画面を新しく作る / 既存の画面を新しい版に更新する |
| Prefab | Unity の部品の型。1 つの型から複数のインスタンスを作り、画像や文字だけ差し替えられる |
| UXP / UPM | Photoshop のプラグインの仕組み / Unity のパッケージの仕組み |
